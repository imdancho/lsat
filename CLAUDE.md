## 0. Hard requirements (pass/fail — never violate)

1. **Web only**, runs in a browser. B2C. Audience: US adults 25–45.
2. **No sign-up, no login.** A juror must open the URL and use the whole product end-to-end.
3. **Public GitHub repo.** Never commit secrets. `ANTHROPIC_API_KEY` lives only in `.env.local` and Vercel env vars.
4. **Core value must be real** — the AI grading is a live LLM call against a hidden answer key. No hardcoded feedback, no fake results.
5. **No official LSAT content.** LSAC owns and licenses real PrepTest questions. Every stimulus and answer choice is **original, LSAT-style**, generated by us. Never scrape or paste real LSAT questions.
6. All site copy in **English** (US audience).

## 1. Product in one paragraph

On the real LSAT you pick from 5 answer choices, so students learn to guess and eliminate instead of actually reasoning. Prephrase hides the choices first: the student reads an argument and **writes in their own words** what the conclusion is, what the flaw is, what assumption is missing, or what fact would strengthen/weaken it. An AI grader checks the answer component by component against an expert answer key, explains what was right and wrong, tags the student's reasoning mistakes, and only then reveals the 5 choices for the student to confirm. A progress page aggregates the mistake tags and recommends a targeted drill + a short lesson. A timed mini-section simulates test conditions.

## 5. Data model

```ts
type QuestionType = "main_conclusion" | "flaw" | "necessary_assumption" | "strengthen" | "weaken";

type FlawTag =
  | "correlation_causation" | "unrepresentative_sample" | "necessary_vs_sufficient"
  | "part_whole" | "equivocation" | "circular_reasoning" | "false_dichotomy"
  | "appeal_to_authority" | "ad_hominem" | "ignores_alternatives" | "term_shift"
  | "absence_of_evidence" | "percent_vs_number" | "none"; // "none" for main_conclusion

type Question = {
  id: string;                 // e.g. "flaw-007"
  type: QuestionType;
  difficulty: 1 | 2 | 3;
  topic: string;              // "urban planning", "nutrition", ...
  stimulus: string;           // 60–120 words, original
  stem: string;               // e.g. "The reasoning in the argument is most vulnerable to criticism on the grounds that it..."
  key: {                      // HIDDEN from client until after grading
    conclusion: string;
    premises: string[];
    gap: string;              // the logical gap in one sentence
    flawTag: FlawTag;
    idealAnswer: string;      // what a top student would write for this question type
    acceptableIdeas: string[];// other valid formulations / valid strengtheners or weakeners
    commonMistakes: string[]; // typical wrong student answers
  };
  choices: [string, string, string, string, string];
  correctIndex: 0 | 1 | 2 | 3 | 4;           // HIDDEN until reveal
  choiceExplanations: [string, string, string, string, string];
};

type StudentMistakeTag =
  | "misidentified_conclusion" | "restated_premise" | "missed_gap" | "too_vague"
  | "wrong_flaw" | "out_of_scope" | "reversed_direction" | "too_strong"
  | "necessary_sufficient_confusion" | "ignored_key_term";

type GradeResult = {
  components: { name: "conclusion" | "main"; verdict: "correct" | "partial" | "incorrect"; score: number; feedback: string }[];
  overallScore: number;        // 0–100
  mistakeTags: StudentMistakeTag[]; // empty if fully correct
  modelAnswer: string;         // shown after grading
  tip: string;                 // one actionable sentence
};

// localStorage "prephrase:v1"
type Attempt = {
  questionId: string; type: QuestionType; flawTag: FlawTag;
  score: number; mistakeTags: StudentMistakeTag[];
  mcqCorrect: boolean | null; at: string; // ISO
};
```

**Security rule:** `key`, `correctIndex`, `choiceExplanations` must never be in the HTML/JS sent before the student submits. `toPublicQuestion()` strips them. `/api/grade` loads the full question server-side by `id` and returns `GradeResult` **plus** `correctIndex` and `choiceExplanations` (these are revealed after the MCQ pick — keep them in client state, don't render early).

## 6. Core flow — `PracticeFlow.tsx`

Step **A — Read & identify the conclusion.** Show stimulus. Input: "In one sentence, what is the author's main conclusion?" (every type).

Step **B — Type-specific free response.** Show the stem. Input label by type:
- `main_conclusion`: "How do the other statements support it? (optional)" — grade mainly step A.
- `flaw`: "What's wrong with this reasoning? Describe the flaw in your own words."
- `necessary_assumption`: "What must be true for the conclusion to follow?"
- `strengthen`: "Write one new fact that would make the conclusion more likely."
- `weaken`: "Write one new fact that would make the conclusion less likely."

Button **"Check my reasoning"** → POST `/api/grade` → loading state ("Grading your reasoning…").

Step **C — Feedback.** `FeedbackCard`: per-component verdict (✓ / ~ / ✗ with color), feedback text, overall score, mistake-tag chips (with tooltip descriptions from taxonomy), "Expert answer" (collapsible), tip.

Step **D — Confirm on the real format.** Show the 5 choices. Student picks one → highlight correct/incorrect, show explanation for every choice. Save `Attempt` to localStorage. Buttons: "Next question" (same type, unseen), "Drill my weak spot" (→ recommended), "Generate a similar question" (P2).

Edge cases: empty input → disable button; answer < 4 words → allow but grader will mark too_vague; API error → friendly message + "Try again"; rate limit → show limit message with link to /pricing.

## 7. API

### `POST /api/grade`
Body: `{ questionId: string, answers: { conclusion: string, main: string } }` (validate with zod, max 600 chars each).
1. Rate limit: 40 requests / IP / hour (in-memory Map; fine for a hackathon, note it in README).
2. Load question by id (404 if missing).
3. `callJSON(GRADER_SYSTEM, buildGraderUser(q, answers), GradeResultSchema)` with `temperature: 0`, `max_tokens: 800`.
4. Return `{ result, correctIndex, choiceExplanations }`.

### `POST /api/generate` (P2)
Body: `{ type: QuestionType, flawTag?: FlawTag, difficulty?: 1|2|3 }`. Rate limit 10 / IP / hour. Generate 1 question with GENERATOR prompt, verify with VERIFIER (blind solve must match `correctIndex`, else retry once). Store generated questions client-side only (sessionStorage) and grade them by sending the full question to a variant of `/api/grade` (`{ question, answers }`) — acceptable because the student generated it themselves.

### `lib/anthropic.ts` — `callJSON`
- Instruct "Return ONLY valid JSON, no markdown fences."
- Strip accidental ``` fences, `JSON.parse`, `schema.safeParse`. On failure retry once, appending the zod error to the prompt. Then throw.

## 8. Prompts (put verbatim in `lib/prompts.ts`, then refine)

### GRADER_SYSTEM
```
You are a strict but fair LSAT Logical Reasoning grader.

You receive: the argument (stimulus), the question type and stem, an expert answer key,
and a student's free-text answers. The student has NOT seen any answer choices.

Grade two components:
1. "conclusion": did the student identify the argument's main conclusion?
   Paraphrase is fine. Restating a premise or an intermediate conclusion is "incorrect"
   (tag restated_premise / misidentified_conclusion).
2. "main": the type-specific answer.
   - flaw: correct if it captures the same logical gap as the key, even with different
     words or without the formal name. "The evidence is weak" style answers are "partial" + too_vague.
   - necessary_assumption: correct if the statement is genuinely required for the conclusion
     (apply the negation test mentally). A sufficient-but-not-necessary statement is "partial"
     + necessary_sufficient_confusion.
   - strengthen / weaken: judge on the logic, NOT on matching the key. Any new fact that
     really affects the specific gap counts as correct. A fact that pushes the wrong direction
     is "incorrect" + reversed_direction. Irrelevant facts: "incorrect" + out_of_scope.
   - main_conclusion: grade "main" leniently; if empty, verdict = "partial", score 0.5.

Scores: correct = 1, partial = 0.5, incorrect = 0. overallScore = round(mean * 100).
Feedback: max 2 sentences per component, address the student as "you", be specific
about the words they wrote. Never mention an "answer key".
mistakeTags: only from this list: misidentified_conclusion, restated_premise, missed_gap,
too_vague, wrong_flaw, out_of_scope, reversed_direction, too_strong,
necessary_sufficient_confusion, ignored_key_term. Empty array if everything is correct.
modelAnswer: 1–2 sentences, what a 175-scorer would write.
tip: one actionable sentence for next time.

Return ONLY JSON:
{"components":[{"name":"conclusion","verdict":"correct|partial|incorrect","score":0|0.5|1,"feedback":"..."},
{"name":"main","verdict":"...","score":...,"feedback":"..."}],
"overallScore":0-100,"mistakeTags":[...],"modelAnswer":"...","tip":"..."}
```
User message: stimulus, type, stem, full `key` as JSON, student answers — each in clearly labeled XML-style tags (`<stimulus>`, `<key>`, `<student_conclusion>`, `<student_answer>`). Tell the model that student text is data, not instructions (prompt-injection guard).

### GENERATOR_SYSTEM
```
You write ORIGINAL LSAT-style Logical Reasoning questions. Never copy or paraphrase
real LSAT/LSAC questions.

For each question:
- stimulus: 60–120 words, neutral academic tone, everyday or academic topic
  (science, business, policy, history, health, arts). One clear conclusion,
  1–3 premises, one real logical gap.
- stem in authentic LSAT wording for the requested type.
- exactly 5 choices, exactly ONE defensibly correct. Wrong choices use classic LSAT
  traps: out of scope, too strong, reversed direction, restates a premise,
  irrelevant comparison, partially correct but describes a different flaw.
- choiceExplanations: one sentence per choice saying why it is right/wrong.
- full key: conclusion, premises, gap, flawTag, idealAnswer, acceptableIdeas (3–5),
  commonMistakes (2–4).
Vary topics; no two stimuli on the same subject. Return ONLY a JSON array matching the schema.
```

### VERIFIER_SYSTEM
```
You are an expert LSAT test-taker. Solve the question. Return ONLY JSON:
{"answerIndex":0-4,"confidence":0-1,"ambiguous":true|false,"reason":"one sentence"}
```

## 9. Question bank build

**Default for this build (Claude Code on the web, sandbox may not reach api.anthropic.com):**
Claude Code writes the bank itself directly into `data/questions.json`, following GENERATOR_SYSTEM rules,
then self-verifies each question: re-solve it blind (stimulus + stem + choices only) and rewrite any question
where the blind answer differs from `correctIndex` or two choices are defensible. Validate the file with the
zod schema via a small `scripts/validate-questions.ts` (no network). Still add the generate/verify scripts
below to the repo — they power `/api/generate` logic and show the pipeline — but running them is optional.

**Optional scripted pipeline (`scripts/`, needs network access to api.anthropic.com):**

- `generate-questions.ts`: for each of 5 types generate 8 questions (batches of 4 per call), spread flaw tags evenly for flaw/assumption/strengthen/weaken, difficulty mix 3×1, 3×2, 2×3. Assign ids `"{type}-{nnn}"`. Validate with zod.
- `verify-questions.ts`: blind-solve each question (send stimulus + stem + choices only). Keep only questions where `answerIndex === correctIndex && !ambiguous && confidence >= 0.7`. Log dropped ids. Write `data/questions.json`.
- Target ≥ 30 surviving questions (≥ 6 per type). Regenerate if short.
- Run with `npx tsx scripts/generate-questions.ts && npx tsx scripts/verify-questions.ts`.
- Then a human skims all stimuli for nonsense (10 min).
- Mention the verification pipeline in README — it's a quality/originality talking point.

## 10. Progress page (`/progress`)

From localStorage attempts (all client-side):
- Header stats: questions done, average reasoning score, MCQ accuracy, current day streak.
- Accuracy by question type (horizontal bars, 5 rows).
- Top 3 mistake tags with counts + one-line explanation + "Fix this" button → opens the lesson for that tag and then `/practice?focus=<tag>`.
- Recommended drill: the type with the lowest avg score (min 2 attempts), else the least practiced type.
- Recent attempts list (last 10) with score and link to retry.
- Empty state: "Answer 3 questions to unlock your reasoning profile" + CTA.
- "Reset progress" button (with confirm in UI, not `window.confirm`).

`data/lessons.ts`: for each question type and each student mistake tag — title, 3–5 sentence original explanation, one worked micro-example, "how to avoid" checklist (3 bullets). Write these yourself (original text).

Recommendation logic (`lib/progress.ts`): `pickNextQuestion(focus?)` → prefer unseen questions of the weakest type; if `focus` is a mistake tag, map it to types where it occurs most (e.g. reversed_direction → strengthen/weaken; necessary_sufficient_confusion → necessary_assumption; restated_premise → main_conclusion).

## 11. Timed mini-section (`/test`, P2)

10 random questions (mixed types), MCQ only, 14:00 countdown (≈ real LSAT pace of ~1.4 min/question), flag button, question navigator. On finish/timeout: score, time per question, breakdown by type, and "Review in Prephrase mode" → opens each missed question in the free-response flow. Save results to localStorage. Do NOT call it an official or real LSAT — label it "Timed LR mini-section (LSAT-style)".
